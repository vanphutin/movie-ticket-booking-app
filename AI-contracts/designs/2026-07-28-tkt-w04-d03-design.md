- **Dependencies/trust boundaries:**
  - **Client ↔ API Gateway Boundary (Untrusted):** Public internet traffic. Gateway validates JWT signature/expiry or routes auth requests to Identity Service.

  - **Microservice ↔ Identity Service DB (Private Data Boundary):** Refresh token hashes and revocation states managed exclusively by Identity Service database schema.

- **Proposed design:**

  ### 1. Proposed Parameters & Configuration Boundaries (Not Hardcoded Contracts)
  - **Proposed Algorithm:** RS256 (Asymmetric RSA 2048-bit). Private Key managed strictly by Identity Service; Public Key distributed to API Gateway and internal services.
    - *Configuration Boundary:* Configurable via `JWT_ALGORITHM` (default `RS256`).
  - **Proposed Access Token Lifespan:** 15 minutes (`exp = iat + 900s`).
    - *Configuration Boundary:* Configurable via `JWT_ACCESS_EXPIRATION_SECONDS` (default `900`).
  - **Proposed Refresh Token Lifespan:** 7 days (`604800s`).
    - *Configuration Boundary:* Configurable via `JWT_REFRESH_EXPIRATION_SECONDS` (default `604800`).
  - **Claims Payload Structure:**
    ```json
    {
      "sub": "<user_uuid>",
      "roles": ["CUSTOMER"],
      "iss": "movie-ticket-booking-identity-service",
      "iat": 1722225600,
      "exp": 1722226500
    }
    ```
  - **Change Condition:** Parameter adjustments do not break effective contracts; they require environment configuration updates (`.env`) or explicit CCR updates.

  ### 2. Authenticated Gateway → Service Boundary (`SEC-004`, `ARCH-008`)
  - **Problem Statement:** Private network isolation and edge header stripping alone do not prove origin to downstream microservices if a service is exposed internally or misconfigured.
  - **Specification:**
    1. API Gateway strips client headers (`X-User-*`).
    2. API Gateway verifies external JWT.
    3. API Gateway computes internal HMAC signature:
       `signature = HMAC-SHA256(X-User-Id + ":" + X-User-Roles + ":" + X-Correlation-Id + ":" + timestamp, INTERNAL_GATEWAY_SECRET)`
    4. API Gateway attaches header: `X-Internal-Gateway-Auth: t=<timestamp>;v=<signature>`.
    5. Downstream microservice middleware verifies `X-Internal-Gateway-Auth` using `INTERNAL_GATEWAY_SECRET` and checks timestamp drift (max 30s).
    6. If signature is invalid or timestamp drifted > 30s, downstream service returns `401 Unauthorized` (`error_code: INVALID_INTERNAL_GATEWAY_AUTH`).

  ### 3. Refresh Token Rotation & Reuse Detection
  - **Token Storage:** Identity Service stores SHA-256 hash of Refresh Tokens in `refresh_tokens` table.
  - **Rotation Algorithm:**
    1. Client presents Refresh Token `RT_1`.
    2. Identity Service verifies `RT_1` hash status is `ACTIVE`.
    3. Identity Service marks `RT_1` as `ROTATED`.
    4. Identity Service issues new `AT_2` (Access Token) and new `RT_2` (Refresh Token) sharing the same `family_id`.
  - **Reuse Detection (Security Trigger):**
    1. Client/Attacker presents `RT_1` (which is in `ROTATED` state).
    2. Identity Service detects token replay/theft (`INV-SEC-04`).
    3. Identity Service immediately sets all tokens associated with `family_id` to `REVOKED`.
    4. Request fails with `401 Unauthorized` (`error_code: TOKEN_REUSE_DETECTED`), requiring re-authentication.

  ### 4. Correlation ID Propagation (`X-Correlation-Id`)
  - If client provides `X-Correlation-Id`, Gateway validates UUID format.
  - If missing or invalid, Gateway generates `X-Correlation-Id: req_<uuid>`.
  - Gateway attaches `X-Correlation-Id` to all downstream HTTP requests, outbox events, and system log entries.
  - Gateway includes `X-Correlation-Id` in all HTTP response headers to clients for end-to-end auditability.

  ### 5. Dependency Timeout & Resiliency Handling
  - Gateway enforces strict timeouts for downstream requests (e.g. 2000ms for Identity Service auth/refresh calls).
  - If Identity Service or DB times out:
    - Gateway logs failure with `X-Correlation-Id` and redacted payload.
    - Gateway returns `HTTP 504 Gateway Timeout` with body:
      ```json
      {
        "status": 504,
        "error_code": "GATEWAY_DEPENDENCY_TIMEOUT",
        "message": "Authentication service response timed out",
        "correlation_id": "req_8f3a9b1c-2d4e-4f6a-8b0c-1d2e3f4a5b6c",
        "timestamp": "2026-07-29T04:15:00Z"
      }
      ```
    - Zero stack trace, zero internal service URL, zero internal IP, and zero secrets exposed.

  ### 6. Comprehensive HTTP Status Code Error Matrix
  - **`401 Unauthorized`**:
    - Missing `Authorization` header on protected route (`error_code: MISSING_TOKEN`).
    - Expired JWT Access Token (`error_code: TOKEN_EXPIRED`).
    - Invalid JWT signature or malformed format (`error_code: INVALID_TOKEN`).
    - Invalid or revoked Refresh Token during refresh (`error_code: INVALID_REFRESH_TOKEN`).
    - Reused Refresh Token detected (`error_code: TOKEN_REUSE_DETECTED`).
    - Missing or invalid internal Gateway HMAC signature at microservice boundary (`error_code: INVALID_INTERNAL_GATEWAY_AUTH`).
  - **`403 Forbidden`**:
    - Authenticated user lacking required role (e.g. CUSTOMER calling `/api/v1/admin/*`, `error_code: INSUFFICIENT_ROLE_PERMISSIONS`).
    - Authenticated user attempting operation on resource owned by another user (e.g. User A cancelling User B's booking, `error_code: RESOURCE_ACCESS_FORBIDDEN`).

  ### 7. Log Redaction Policy & Zero Data Leakage (`SEC-007`)
  - **Target Headers:** `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Refresh-Token`, `X-Internal-Gateway-Auth`.
  - **Target Body Keys:** `password`, `old_password`, `new_password`, `refreshToken`, `accessToken`, `client_secret`, `credit_card_number`, `cvv`.
  - **Sanitization Rule:** Replace target values with `"[REDACTED]"`.
  - **Leakage Prevention Audit:** System logs and HTTP response bodies must NEVER contain:
    1. Plaintext or hashed JWT signatures / secrets.
    2. Session cookies or refresh token strings.
    3. User PII (email, phone, address) in raw unredacted log lines.
    4. Internal microservice URLs, internal IP addresses (`10.x.x.x`, `172.x.x.x`), or stack traces in API error payloads.

- **Service owner; domain/application/adapter/transport impact:**
  - **Service Owner:** API Gateway (Edge Pipeline & Internal HMAC Signing) & Identity Service (Token Lifecycle & Revocation).
  - **Transport Impact:** Internal HTTP request headers augmented with `X-User-Id`, `X-User-Roles`, `X-Correlation-Id`, and `X-Internal-Gateway-Auth`.
  - **Application/Domain Impact:** Microservices verify `X-Internal-Gateway-Auth` before consuming `X-User-Id` for domain resource authorization.
  - **Infrastructure Impact:** Environment secrets (`INTERNAL_GATEWAY_SECRET`, RSA Public/Private Key pairs) configured across deployments.

- **Ports, adapters and composition root:**
  - **Token Signer Port:** Identity Service RSA Private Key Adapter.
  - **Token Verifier Port:** Gateway RSA Public Key Adapter.
  - **Internal Auth Signer/Verifier Port:** Gateway/Service HMAC-SHA256 Adapter.
  - **Token Storage Port:** Identity Service Refresh Token Repository Adapter (PostgreSQL).

- **Cross-service contracts and forbidden dependency checks:**
  - Direct database sharing between Gateway and Microservices is strictly forbidden (`ARCH-013`).
  - Client-supplied `X-User-*` headers must never reach downstream services (`INV-SEC-02`).
  - Downstream services must reject incoming calls lacking valid `X-Internal-Gateway-Auth` (`SEC-004`, `ARCH-008`).

- **Rejected alternative and reason:**
  - **Rejected Alternative 1:** HS256 (Symmetric Key) across all microservices.
    - *Reason:* Exposing secret signing key to edge Gateway nodes creates severe security risk; if Gateway is compromised, attackers can forge arbitrary tokens.
  - **Rejected Alternative 2:** Relying solely on private network boundaries without internal Gateway authentication (`X-Internal-Gateway-Auth`).
    - *Reason:* Violates zero-trust principle (`SEC-004`, `ARCH-008`); private network topology does not prove header origin.

- **Trade-off/limitation:**
  - **Trade-off:** Computing internal HMAC signature (`X-Internal-Gateway-Auth`) adds ~0.1ms latency per internal hop, but provides cryptographically verified origin isolation.
  - **Limitation:** Stateless JWT Access Tokens cannot be individually revoked before 15-minute expiration without stateful blacklisting (mitigated by short 15-minute token lifespan).

- **API/data/event delta:**
  - **API Delta:** Internal HTTP requests downstream contain `X-User-Id`, `X-User-Roles`, `X-Correlation-Id`, and `X-Internal-Gateway-Auth`.
  - **Schema Delta:** `refresh_tokens` table schema verified in `TKT-W04-D02` (`id`, `user_id`, `token_hash`, `family_id`, `status`, `expires_at`, `created_at`).
  - **Event Delta:** Security audit log events generated on token reuse detection (`TOKEN_FAMILY_REVOKED`).

- **Failure/security cases:**
  - Client sends forged `X-User-Id` header → Gateway strips header before forwarding.
  - External request attempts to bypass Gateway directly to microservice → Microservice rejects request due to missing/invalid `X-Internal-Gateway-Auth` HMAC signature (`401 Unauthorized`).
  - Replayed Refresh Token → Identity Service invalidates entire token family and returns `401 Unauthorized`.
  - Expired JWT → Gateway returns `401 Unauthorized` with `token_expired` error payload and correlation ID.
  - Identity Service timeout (>2000ms) → Gateway returns `504 Gateway Timeout` without leaking stack traces or internal URLs.

- **Review findings:**
  - `D03-DESIGN-F01` (`BLOCKER`): `X-Internal-Gateway-Auth` signs only actor claims, correlation ID and a timestamp. It does not bind the HTTP method, canonical path, target service or body digest, and it defines no nonce/replay cache. A captured signature can therefore be replayed within the 30-second window or redirected to a different operation. Define canonical signing input, target/audience binding, constant-time verification, key rotation/versioning and an enforceable replay control; add negative tests for replay, cross-route substitution and stale/key-version failures.
  - `D03-DESIGN-F02` (`HIGH`): Error examples use top-level `status`, `error_code`, `correlation_id` and `timestamp`, which conflicts with the mandatory `API-COM-003` envelope `{ "error": { "code", "message", "requestId", "details"? } }`. Normalize the 401/403/504 matrix and all sequence examples to the contract envelope without exposing internal details.
  - `D03-DESIGN-F03` (`HIGH`): Logout sequences and tests return `200 OK`, while `API-AUTH-004` requires `204` with an empty response and replay-safe behavior. Change both first and repeated successful logout outcomes to `204 No Content`.
  - `D03-DESIGN-F04` (`HIGH`): Correlation validation requires a UUID but generated values use `req_<uuid>`, which is not a UUID. Select one canonical format and use the `requestId` mapping required by `API-COM-003` consistently.
  - `D03-DESIGN-F05` (`HIGH`): The rollback plan permits reverting authenticated Gateway-to-service validation to an unspecified previous static configuration. That can violate `SEC-004` and `ARCH-008`. Rollback must preserve authenticated internal identity, such as dual-key overlap/key-version rollback, and must never restore unauthenticated trust in actor headers.
