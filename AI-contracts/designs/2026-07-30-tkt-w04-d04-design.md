## Invariants

1. Public request DTOs are strict allowlists and reject unknown fields.
2. No request may assign role, status, verification state, actor identity, session
   ownership or token-family identity.
3. Password and token values are never normalized, echoed, logged or placed in error
   details.
4. External actor headers are untrusted. `/me` resolves the actor only from the
   authenticated Gateway-to-Identity context.
5. Authentication/session failures are neutral and do not reveal account existence,
   refresh replay or session ownership.
6. Every non-empty error follows `API-COM-003` and contains a request correlation ID.
7. Register idempotency produces at most one registration effect for a key/payload
   pair, including concurrent and unknown-outcome retries.
8. Logout remains possible after access-token expiry and is replay-safe.

## 1. Request components

### `RegisterRequest`

```yaml
type: object
additionalProperties: false
required: [email, password, displayName]
properties:
  email:
    type: string
    format: email
    maxLength: 254
  password:
    type: string
    format: password
    minLength: 12
    maxLength: 128
    writeOnly: true
  displayName:
    type: string
    minLength: 1
    maxLength: 100
```

- Email is trimmed and lowercased for canonical comparison.
- Display name is trimmed while preserving Unicode and case.
- Password is preserved byte-for-byte; it is never trimmed, lowercased or implicitly
  Unicode-normalized.
- Public registration creates only `CUSTOMER`; no role input exists.

### `LoginRequest`

```yaml
type: object
additionalProperties: false
required: [email, password]
properties:
  email:
    type: string
    format: email
    maxLength: 254
  password:
    type: string
    format: password
    minLength: 1
    maxLength: 128
    writeOnly: true
```

Login does not re-apply the current registration minimum to an existing credential.

### `RefreshRequest` and `LogoutRequest`

Each component has the same boundary but remains a separate use-case type:

```yaml
type: object
additionalProperties: false
required: [refreshToken]
properties:
  refreshToken:
    type: string
    minLength: 1
    maxLength: 2048
    writeOnly: true
```

Refresh tokens are opaque. Neither request accepts an access token, user ID, session ID
or token-family ID in the body.

## 2. Response components

### `AuthSessionResponse`

```yaml
type: object
additionalProperties: false
required: [accessToken, refreshToken, tokenType, expiresIn, user]
properties:
  accessToken:
    type: string
    minLength: 1
    readOnly: true
  refreshToken:
    type: string
    minLength: 1
    readOnly: true
  tokenType:
    type: string
    enum: [Bearer]
    readOnly: true
  expiresIn:
    type: integer
    minimum: 1
    description: Remaining access-token lifetime in seconds.
    readOnly: true
  user:
    $ref: '#/components/schemas/SessionUserResponse'
```

### `SessionUserResponse` and `ProfileResponse`

Both currently expose `id`, `email`, `displayName` and `roles`, but are separate
components so the session snapshot and `/me` representation can evolve independently.

```yaml
type: object
additionalProperties: false
required: [id, email, displayName, roles]
properties:
  id:
    type: string
    format: uuid
    readOnly: true
  email:
    type: string
    format: email
    readOnly: true
  displayName:
    type: string
    minLength: 1
    maxLength: 100
    readOnly: true
  roles:
    type: array
    minItems: 1
    uniqueItems: true
    readOnly: true
    items:
      $ref: '#/components/schemas/UserRole'
```

`UserRole` contains only `CUSTOMER` and `ADMIN`. `STAFF` is excluded from the MVP under
`SEC-013`. Successful logout is `204 No Content` with no representation.

## 3. Error components

```yaml
ErrorResponse:
  type: object
  additionalProperties: false
  required: [error]
  properties:
    error:
      $ref: '#/components/schemas/ErrorObject'

ErrorObject:
  type: object
  additionalProperties: false
  required: [code, message, requestId]
  properties:
    code:
      type: string
      minLength: 1
      maxLength: 100
      pattern: '^[A-Z][A-Z0-9_]*$'
    message:
      type: string
      minLength: 1
      maxLength: 500
    requestId:
      type: string
      minLength: 1
      maxLength: 128
    details:
      $ref: '#/components/schemas/ErrorDetails'
```

`ErrorDetails.fields` is a bounded array of `FieldViolation` objects containing
`field`, `code` and `message`. Field violation codes are:

- `REQUIRED`
- `INVALID_TYPE`
- `INVALID_FORMAT`
- `INVALID_VALUE`
- `OUT_OF_RANGE`
- `TOO_SHORT`
- `TOO_LONG`
- `UNKNOWN_FIELD`

Validation returns all safe violations in deterministic schema/request order.
Authentication and session failures never include field details. Errors never expose
submitted secrets, stack traces, framework exceptions, SQL errors or internal URLs.

Public operation codes are:

| HTTP | Codes |
|---:|---|
| `400` | `VALIDATION_FAILED`, `MALFORMED_JSON`, `IDEMPOTENCY_KEY_REQUIRED` |
| `401` | `INVALID_CREDENTIALS`, `INVALID_REFRESH_TOKEN`, `AUTHENTICATION_REQUIRED`, `ACCESS_TOKEN_EXPIRED`, `INVALID_ACCESS_TOKEN` |
| `409` | `REGISTRATION_CONFLICT`, `IDEMPOTENCY_KEY_CONFLICT` |
| `415` | `UNSUPPORTED_MEDIA_TYPE` |
| `429` | `RATE_LIMIT_EXCEEDED` |
| `500` | `INTERNAL_ERROR` |
| `503` | `SERVICE_UNAVAILABLE` |

The five auth operations have no public `403`: register/login are public,
refresh/logout authenticate with a refresh credential, and `/me` is self-only.
Deny-by-default remains mandatory for later role/resource endpoints.

## 4. Header and media-type components

Register requires an `Idempotency-Key` header:

```yaml
name: Idempotency-Key
in: header
required: true
schema:
  type: string
  minLength: 16
  maxLength: 128
  pattern: '^[A-Za-z0-9._:-]+$'
```

The key is opaque, case-sensitive and contains no PII. Every response contains
`X-Request-Id`, a bounded non-empty string matching `error.requestId` on an error.
`429` also includes an integer-seconds `Retry-After` header.

Operations with a body accept `application/json`. Malformed JSON maps to
`400 MALFORMED_JSON`; an unsupported request media type maps to
`415 UNSUPPORTED_MEDIA_TYPE`. Logout `204` has no content type or body.

## 5. Operations and security

```yaml
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
```

| Operation ID | Route | Security | Success | Contracted failures |
|---|---|---|---:|---|
| `registerCustomer` | `POST /api/v1/auth/register` | public, rate limited, idempotency key | `201 AuthSessionResponse` | `400`, `409`, `415`, `429`, normalized `500/503` |
| `loginCustomer` | `POST /api/v1/auth/login` | public, rate limited | `200 AuthSessionResponse` | `400`, neutral `401`, `415`, `429`, normalized `500/503` |
| `refreshSession` | `POST /api/v1/auth/refresh` | refresh credential, rate limited | `200 AuthSessionResponse` | `400`, neutral `401`, `415`, `429`, normalized `500/503` |
| `logoutSession` | `POST /api/v1/auth/logout` | refresh credential | `204` | `400`, neutral `401`, `415`, normalized `500/503` |
| `getMyProfile` | `GET /api/v1/me` | `bearerAuth` | `200 ProfileResponse` | `401`, normalized `500/503` |

The four non-Bearer operations explicitly use `security: []` so they do not inherit a
global Bearer declaration. Refresh/logout remain credential-protected through their
write-only request field.

## 6. Session and idempotency behavior

### Refresh

- A valid active refresh token is consumed and rotated.
- Success returns a completely new `AuthSessionResponse`.
- The client replaces both credentials atomically.
- Invalid, expired, revoked and replayed tokens all return the same public
  `401 INVALID_REFRESH_TOKEN`.
- Reuse still triggers the D03 token-family revocation invariant internally.

### Logout

- Logout requires only the refresh token, so it remains usable after access-token
  expiry.
- An active owned session is revoked and returns `204`.
- Repeating logout with the recognized revoked token returns `204` without another
  effect.
- Malformed, expired or unrecognized credentials return neutral `401`.
- A bounded revocation tombstone is retained long enough to support replay-safe logout.

### Registration idempotency

- Fingerprinting uses the validated, canonical DTO plus `operationId`, not raw JSON
  property order.
- Email and display name use their canonical values; password bytes remain exact.
- Only a cryptographic payload fingerprint is persisted, never the plaintext password.
- Same key/same canonical payload returns the original logical `201` outcome.
- Same key/different payload returns `409 IDEMPOTENCY_KEY_CONFLICT`.
- Same email with another key returns neutral `409 REGISTRATION_CONFLICT`.
- Concurrent same-key requests produce at most one registration effect.
- To replay the original session response without issuing another session, the response
  is encrypted at rest for a bounded idempotency window. Proposed default retention is
  24 hours and remains configurable.

## 7. Deny and disclosure matrix

| Attempt | Public result | Required control |
|---|---|---|
| Register with `roles`, `isAdmin`, `status`, `userId` or verification state | `400 VALIDATION_FAILED` | Strict DTO allowlist |
| Login with unknown email or wrong password | identical `401 INVALID_CREDENTIALS` shape | Neutral status/code/message/details and comparable handling |
| Refresh a replayed token | neutral `401 INVALID_REFRESH_TOKEN` | Internal family revocation without replay disclosure |
| Logout after access-token expiry | refresh credential may still produce `204` | No access-token dependency |
| `/me` without a valid Bearer token | `401`, no profile | Authenticated context required |
| Supply `X-User-Id`, `X-User-Roles` or body/query actor ID | ignored/stripped as identity; dangerous body fields rejected | Actor comes only from authenticated internal context |
| Public registration requests Admin | `400` | Public role is fixed to Customer |

Register's contracted `409` remains a residual account-enumeration signal. Neutral
message/code, rate limiting and abuse monitoring mitigate but do not eliminate it.

## 8. Contract-test matrix

### Static OpenAPI

- Parse the document and resolve every `$ref`.
- Require unique operation IDs and the documented security declaration per operation.
- Require `additionalProperties: false` on requests and exclude forbidden fields.
- Verify status/response mappings, error envelope use and empty logout `204`.

### Schema fixtures

- Validate one success fixture per non-empty success response.
- Reject missing fields, unknown fields, wrong types, bad formats and every bound.
- Verify deterministic safe field violations.
- Verify passwords, raw tokens, token hashes, session-family IDs, stack traces and
  internal URLs do not appear outside explicitly allowed credential fields.

### Behavioral contract

- Compare unknown-email and wrong-password login failures.
- Exercise register same-key/same-payload, same-key/different-payload, different-key
  conflict, concurrent duplicate and crash/unknown-outcome retry.
- Exercise refresh rotation, expiry, revocation and replay/family revocation.
- Exercise active and repeated logout.
- Exercise `/me` missing, expired, invalid-signature and valid access tokens.
- Prove spoofed actor headers/body/query values cannot change the resolved actor.
- Verify `429` envelope plus `Retry-After` and normalized infrastructure errors.

### Required negative fixtures

- `roles: ["ADMIN"]`, `isAdmin: true`, `status: "ACTIVE"` and another user's `userId`
- spoofed `X-User-Id` and `X-User-Roles`
- empty and oversized credentials
- malformed JSON and unsupported content type
- concurrent requests sharing one idempotency key

These are planned tests, not observed runtime evidence.

## 9. Compatibility, rollback and change conditions

Breaking changes requiring a version or approved CCR include removing/renaming a field,
tightening optional to required, changing a type or meaning, changing an existing error
code, moving refresh credentials to cookie-only delivery and removing a documented
outcome. Optional response fields require consumer review. Adding an enum role also
requires compatibility review because generated consumers may use exhaustive matching.

Rollback must preserve strict DTO rejection, neutral credential errors, idempotency
outcomes and trusted actor resolution. If no compatible secure contract/implementation
exists, the affected operation fails closed; rollback must not restore permissive DTOs,
detailed authentication failures or client actor headers.

Reconsider JSON refresh-token delivery only after a web-client review defines
`HttpOnly`, `Secure`, `SameSite`, CSRF, CORS and logout semantics. Reconsider the
12-character registration minimum only with an explicit usability/security decision
and equivalent credential-strength control.

## 10. Rejected alternatives and trade-offs

- **Shared persistence/request/response `UserDto`:** rejected for mass assignment and
  data leakage.
- **Ignore unknown fields:** rejected because it hides client drift and privilege fields.
- **Detailed account/token failure codes:** rejected because they enable enumeration
  and disclose security response.
- **Require a valid access token for logout:** rejected because it forces refresh solely
  to revoke a session.
- **Hash raw JSON for idempotency:** rejected because property order and normalized
  fields create false conflicts.
- **Issue a new session for a register retry:** rejected because it violates the same
  logical outcome.
- **Cookie-only refresh credential now:** deferred because the required browser-security
  contract is outside the ticket.

The selected design increases upfront schema/test work and requires encrypted
short-lived idempotency response storage. In exchange, it produces deterministic
consumer behavior, prevents mass assignment, limits authentication disclosure and
supports safe retries.
